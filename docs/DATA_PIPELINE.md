# ゲームデータの更新基盤

## 実装状況

`codex/tarkov-modernization`でデータ基盤・条件判定・画面接続・プロフィール保存を実装した。グラフ・一覧・詳細・FiR・ハイドアウトは新スナップショットを使う。古い画面と各画面の独立した保存処理は削除し、共通のプロフィールストアと判定へ置き換えた。

データ元は [tarkov.dev JSON API](https://json.tarkov.dev/endpoints)。通常、PvE、PvPシーズンの3モードを独立して保存する。シーズンIDが変わってもユーザーの進捗を自動削除しない。

## ローカル実行

Node.js 24とnpmを使用する。追加のAPIキーは不要。

```sh
npm ci
npm test
npm run typecheck
npm run data:update
```

単一モードを確認する場合:

```sh
npm run data:update -- --mode=regular
```

`public/game-data/manifest.json`が採用中の版を示す。各モードのファイル名はデータ内容のSHA-256で、過去版を残して新しいmanifestを最後に置き換える。差分は追加・削除・変更されたタスクID、関連データの変更有無、直前の版への参照を含む。

`.cache/tarkov-api`に応答本文・ETag・Last-Modifiedを保存し、Gitには含めない。304応答では本文を再取得しない。価格やトレーダーのリセット時刻だけが変わっても、管理対象データの版は変えない。実APIで、全45リソース中43件が304、2件は取得されたが意味のある変更がなく、manifestが書き換わらないことを確認した。

キャッシュがない初回やキャッシュの失効時には全文取得が必要。差分配信APIではないため、ETagが変わったリソースも全文を取得する。全モードのtasks・traders・hideout・items・mapsと日英辞書を、最大3件ずつ並列取得する。

## 検証と障害時

タスク・トレーダー参照、条件種別、翻訳パス、目標ID、以前のスナップショットの整合性を検証する。タスク数の20%超の減少や未対応の条件種別は更新を中止する。会話条件と内部変数はデータを保持し、利用者の確認がない限り解放済みと断定しない。

1モードでも失敗すると、新しいmanifestは公開しない。ネットワーク失敗・429・5xxは回数を制限して再試行する。以前の正常版とキャッシュを残す。中断時に参照されない候補ファイルが残る場合はあるが、manifestの採用版は変わらない。

異常な大幅変更が実際のゲーム仕様変更なら、変更内容を調査して検証ロジック・fixtureを修正する。検証を無効化して自動採用しない。

## GitHub Actions

`.github/workflows/update-game-data.yml`がUTCの0:17、6:17、12:17、18:17（日本時間9:17、15:17、21:17、3:17）に確認する。GitHub側の混雑で実行時刻が遅れる場合がある。API本文とHTTP検証子はActions cacheに保存し、次回復元する。

意味のある変更がある場合だけ、テスト・型チェック・ビルドを通したデータをmainへ通常のpushで保存し、再利用可能なPagesワークフローを呼び出す。GITHUB_TOKENのpushから通常のpushワークフローは発火しないため、明示的な呼び出しで同じデータコミットを配信する。変更がなければコミット・配信を省略する。

有効化には、ワークフローをデフォルトブランチのmainにマージし、Actionsを有効にする。mainへのActionsの書き込みがブランチ保護で禁止されている場合は更新コミットが失敗するため、リポジトリの運用設定を確認する。現在はローカルでコミットした段階で、リモートへのpush・定期実行・公開は行っていない。

仕様の出典: [scheduleの制約](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)、[GITHUB_TOKENによる再帰実行の抑止](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)、[再利用可能ワークフロー](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)。

## 条件判定

`src/domain/progression.ts`に画面から独立した判定を置く。PMCレベル、実際の前提タスク状態（受注中・完了・失敗）、LL、信頼度、陣営、プレステージ、確認が必要な条件、起点を明示記録した待機時間を扱う。

判定結果は「条件を満たす」「既知の未達条件がある」「確認が必要」の3状態。手動で記録したゲーム内の受注可否は別に保持し、既知の不足理由を消さない。未入力の信頼度を0とみなさず、LL計算にも未解放・不明を反映する。APIの内部変数から未検証の配布グループのOR条件を推測しない。

30件のテストで、条件の境界値、未知条件、304・HTTP失敗、翻訳と代替品の保持、内容ハッシュ、モード途中の失敗、以前の版の破損、プロフィール移行・復元・シーズン分離、グラフの循環、アイテムの集計を確認する。CIでは全体のlint・型チェック・ビルドも実行する。

## プロフィールと画面

`tarkov-helper-profiles-v1`にスキーマ付きの全プロフィールを保存する。通常・PvE・シーズンID別に分離し、未知のタスクIDや割当が不明な旧アイテム記録も残す。旧完了タスク・PMCレベル・アイテム記録・非対象の施設は初回だけ読み取る。旧キーの変更・削除はしない。

旧アイテム記録は同じアイテムが複数の納品目標に使われる場合に自動割当しない。代替候補への記録は1目標の合計数として上限まで移行する。旧施設の完了記録はIDを保持したうえで建設済みレベルへ反映する。未割当の記録はバックアップに保持し、画面で件数を表示する。

保存の失敗や破損時はエラーを表示し、既存データを黙って上書きしない。復元ではスキーマ・数値・状態・IDを検証し、プロフィールごとの完了数を表示してから利用者が適用する。同じタブには即時通知し、別タブのstorageイベントも反映する。

ブラウザはmanifestを起動時・プロフィール変更時・手動再確認時に取得する。スナップショットのSHA-256・モード・シーズン・スキーマを検証してから採用する。古いシーズンのプロフィールには最後に使った版を残し、現在のシーズンへ進捗を転用しない。

日英タスク／アイテム検索、お気に入り、未完了・受注中・要確認フィルター、APIフラグによるKappa／Lightkeeper関連表示、マップ別の受注中の未完了目標、キー候補の重複集約、マーカーの消耗数量を実装した。施設と納品目標へのアイテム割当は別々に記録する。

残る検証・拡張: 配布グループのOR条件とLightkeeper入口の補正、更新差分の名前付き履歴と既読管理、レイドの任意目標選択・複雑な装備指定、複数タブの同時書き込みの競合解決、端末内の最終正常スナップショットの永続キャッシュ。現在の再取得失敗では同じページで最後に読み込めたデータを残すが、ブラウザ終了後の完全オフライン動作は保証しない。

依存関係はNext.jsと対応するESLint設定を16.3.8へ更新し、互換性を保てるロックファイルの修正を適用した。本番依存のnpm監査は0件。開発依存には、ESLintの間接依存bracesに修正版がない問題が残る（監査では5パッケージに伝播して表示）。Next.js用のESLint設定を14系へ戻す強制修正は行わない。出典: [Next.jsのWindowsサーバーに関する修正](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36)。
# タスク状態による信頼度の記録とLL列

完了時は `finishRewards.traderStanding`、失敗時は `failureOutcome.traderStanding` の全トレーダー分を符号付きで反映する。参照形式は [tarkov.dev APIのスキーマ](https://github.com/the-hideout/tarkov-api/blob/main/schema-static.mjs) と保存済みJSONで確認した。受注時報酬はこの処理の対象外。未入力の信頼度は0から加算するので、実際の現在値はトレーダー設定から調整する。

プロフィールの `taskReputation` に実際に反映した差分を保存する。同一状態への再設定は何も加算しない。取り消し・失敗への変更では記録した旧差分だけを戻して新差分を反映し、手動調整や後のAPI報酬変更を保護する。既存の完了済みタスク・復元データには遡って加算しない。

グラフは左からLL1〜LL4、LL要確認の列に配置する。本人トレーダーの明示LL条件を満たす最小LLを使用し、他トレーダーの条件や残るタスク前提は詳細と依存線に保持する。明示LL条件がなく内部条件があるタスクはLL要確認へ、両方ないものはLL1へ置く。LL1列はすべて受注可能という意味ではなく、PMCレベル・前提タスクなどの判定は別途行う。

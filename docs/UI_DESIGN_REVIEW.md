# Tarkov Helper：AIらしく見える理由とUI改善方針

調査日：2026年10月19日。今回は調査と提案のみ。アプリの表示や操作は変更していない。

## 1. 調査から言えること

「AI臭」は統一された評価指標ではない。外観から制作手段を断定するための基準として扱うべきではない。この文書では、ネットで指摘される傾向、既存のUI設計原則、現在の画面への評価を分けて扱う。

Anthropicは、指示の少ないフロントエンド生成が、よくある書体や紫のグラデーションなどの無難なパターンへ収束すると説明している。ただし、これはベンダーによる説明と作例であり、あらゆるAI製サイトに共通する原因を実験的に証明したものではない。[Improving frontend design through Skills](https://claude.com/resources/articles/improving-frontend-design-through-skills)

重要なのは、汎用的なパターン自体を避けることではない。操作の慣習は共有した方が使いやすい。NN/gの評価軸には一貫性、既存の慣習との整合、必要な情報への集中などがある。見慣れた操作と、目的に合わせた情報設計を両立させる。[10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)

## 2. よく挙げられる特徴と、その受け取り方

| よくある指摘 | なぜ人工的・試作品的に感じられるか | このアプリへの関係 |
| --- | --- | --- |
| 定型の色・フォント・カード構成 | 別の製品へ名前だけ差し替えられそうに見える | 紫のグラデーションはない。一方、紺色・角丸・細い枠が広く使われている |
| 何でもカードや枠に入れる | 機能同士の重要度の違いが見えにくい | ヘッダー、進捗、入力欄、一覧が連続した箱に見えやすい |
| 小さく薄い文字が多い | 情報はあるが、読むべき場所が定まらない | 11〜12pxの補助情報が多く、判断に必要な情報まで控えめになっている |
| 多色のラベル・注意書き | どれを優先すべきかを毎回読む必要がある | 黄・水色・赤・緑が並び、色の役割が競合しやすい |
| 操作方法を文章で説明する | 操作部品自体の分かりやすさが不足して見える | グラフのクリック操作、予測と記録の違い、データ事情の説明が同居する |
| ページごとに細部が違う | 完成品より、別々の試作品の集合に感じられる | ヘッダーは直前の修正で共通化済み。他の表示ルールにも同じ考え方が必要 |

右2列は現在の画面と実装を踏まえた評価・仮説であり、ユーザーテストの結果ではない。角丸、ダークテーマ、Tailwind、特定のフォントの使用だけでAIらしさが決まるわけではない。

視覚的な完成度を考える際、NN/gは文字、階層、配色、整列などの一貫した扱いを示している。見た目を特殊にするより、重要なものが先に読める状態を作る方が今回の目的に合う。[Why Does a Design Look Good?](https://www.nngroup.com/articles/why-does-design-look-good/)

## 3. 現在のTarkov Helperで特に大きい要因

### 判断の中心が小さな補助情報に分散している

このアプリの中心は「あと何件で次のタスクが出るか」「LLまで何が不足しているか」「どのタスクから進めるか」。しかし、現在はタスク名、概要、信頼度、次のLL、完了数の目安が似た強さで並ぶ。初見で視線の行き先が決まりにくい。

次のLLと不足を一つのまとまりとして読めるようにし、その次にタスク一覧へ視線を流す。例として「LL2まで　信頼度あと0.12　／　レベルあと2」のような短い表示を検討する。件数が目安なら、その意味を残し、確定条件と混同させない。

### 背景・枠・強調色の使い方が均質になっている

箱の形が整っていても、すべて同じ囲い方だと、背景・操作・主情報が同格に見える。固定ヘッダーとデータ領域を主な区切りとし、補助情報は余白や整列でまとめる方向がよい。

Atlassianは色を装飾名ではなく、通常、主要操作、情報、成功、警告、危険といった意味で整理している。ここから得られるのは「赤を禁止する」ことではなく、各色の用途を固定する考え方である。[Color roles](https://atlassian.design/foundations/color)

ロックを薄い赤、完了を緑で表示するという現在の要件は維持できる。改善案は、背景の面積・濃さを抑える、グループ見出しと内部行で強さを変える、といった調整。赤が通常のロックとエラーの双方に使われる場合は、文字やアイコンでも区別する。

### 実装事情を説明する文章が主画面に出ている

「条件予測とゲーム内で記録した状態は別」「同名タスクもIDごとに表示」などは、正確さのための説明として意味がある。ただし、毎回読む主情報ではない。常設は件数や状態の短い表示にし、詳しい根拠・データの事情はヘルプや要確認の説明へ移す。

NN/gの段階的開示は、主要な操作を先に出し、必要になった段階で詳細へ進める考え方。ただし、常用操作まで隠して記憶に頼らせることは避ける。[Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)

### 要素の共通化と、デザインの共通化がまだ別々になっている

WorkspaceHeaderの共通化はできた。一方、文字の役割、余白、枠、状態色の基準は、部品を共有するだけでは揃わない。私の実装でも機能・説明を追加する調整を重ねる一方、画面全体の優先順位と見た目の規則を先に固め切れていなかった。

今後は背景、文字、境界線、操作色、状態色、文字サイズ、余白、角丸を名前付きの共通設定として扱う。Atlassianのデザイントークンは、こうした判断を一箇所で管理する既存の仕組みの例。[Foundations](https://atlassian.design/foundations)

## 4. すでにある参考先・解決手段

| 参考先 | 借りるもの | このアプリでの判断 |
| --- | --- | --- |
| [Carbon Design System：Data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines) | 表の密度、ソート、行操作、展開の慣習 | 最も直接参考になる。ライブラリ全体の導入を前提にせず、表の設計を借りる |
| [Atlassian Design System](https://atlassian.design/foundations) | 色・文字・余白・状態表示を共通ルールとして管理する方法 | ページをまたいだ統一に向く。ブランド用フォントまでコピーする必要はない |
| [Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/introduction) | フォーカス、キーボード操作、ポップアップ等の挙動の土台 | 将来、複雑な部品を整備する場合の候補。見た目を決める製品ではない |
| [Anthropicのフロントエンド設計ガイド](https://claude.com/resources/articles/improving-frontend-design-through-skills) | 汎用的な既定値を避け、方向性を再利用可能な指示へまとめる考え方 | 参考にはなるが、強い装飾やアニメーションの推奨を管理アプリへそのまま移さない |

Carbonは複数の行高と、ソート・展開などの慣習を文書化している。現在のタスク行は基本80pxなので、主要情報を1〜2行へ整理したうえで、48〜64px程度の案を比較する価値がある。これは今回の仮案であり、Carbonの数値をそのまま強制する提案ではない。

Radixは見た目のない部品の土台を提供する。導入しても、何を強く見せるか、どの情報を残すかは別途決める必要がある。現在のアプリは独自のTailwindベースなので、特定のUIライブラリを置き換えるだけの解決にはならない。

## 5. このアプリに合う方向性

提案する方向は「ゲーム中に横へ置く、読み取りやすいタスク管理ツール」。宣伝用ページのような大きな装飾より、繰り返し使える一覧の品質を優先する。

- ダークテーマは維持。紺色の比率を下げた炭色・グレーも比較候補とする。
- 強調色は主に1系統。状態色は赤・緑などの意味を固定し、通常表示では広い面積に使わない。
- タスク名・不足数・次のLLを主情報とする。Map・FiRは走査しやすい位置に揃える。
- 文字は本文14px前後、補助情報12px前後を出発点に比較。重要情報を小さくして詰め込まない。[Atlassian Typography](https://atlassian.design/foundations/typography)
- トレーダーとFiRの画像中心の表示、固定ヘッダー、Wikiへの導線、全体グラフは維持。
- 普遍的に分かりにくい操作には短いラベルや説明を付ける。慣れたゲーム画像と、意味の曖昧な操作アイコンは分けて考える。[Recognition and Recall](https://www.nngroup.com/articles/recognition-and-recall/)
- 日本語の書体、英語タスク名、数字の表示を実画面で確認する。フォント名だけを交換して終わりにしない。

これは見た目の好みを含む提案。暗色・角丸・赤いロック表示などを一律に悪いとするものではない。また、コントラストの適否はこの調査で測定していないため、具体的な色を決める段階で確認する。

## 6. 改善の順序

1. **主情報の優先順位を決める。** トレーダーの不足情報とタスク名が最初に読めるかを整理する。常設の長い説明は必要な場所へ移す。
2. **1ページだけで見た目を比較する。** Praporの現在表示を残し、同じデータ・同じ画面幅で、文字・余白・境界線・状態色を揃えた案を作る。
3. **共通ルールを確定する。** 色、文字、行高、操作領域、ポップアップの出方を短い設計ルールと共通設定へまとめる。
4. **他ページへ適用する。** 先に部品を揃え、グラフ・FiR・マップ別で別の見た目が増えないようにする。
5. **実際の操作で比較する。** 「LLまでの不足を知る」「特定マップで進めるタスクを探す」「FiRを記録する」の3操作で迷いと手数を見る。

完成の判断は「AIらしく見えなくなった気がする」だけにしない。見るべき情報が分かるか、操作に迷わないか、完了とロックを取り違えないか、文字やポップアップが読めるかを確かめる。

## 7. 今回は勧めない対策

- フォントやアクセント色だけを変え、情報の並びをそのままにする。
- AI対策という理由だけで、グラデーション・角丸・既存のUI部品を禁止する。
- 個性を出すためにアニメーション、装飾画像、ガラス風背景を足す。
- 情報を減らすために、必要な不足条件や編集方法まで隠す。
- 高機能なUIライブラリへ全面移行し、それ自体をデザイン改善と考える。

必要なのは、日常的に使う人が見る順番と操作の慣習に沿って、少数の設計判断を画面全体へ徹底すること。現状の機能を残したままでも改善できる。

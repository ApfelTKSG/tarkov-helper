# Tarkov Helper 現行仕様対応・内部整理計画

調査日: 2026-10-06（日本時間）。本書は実装計画であり、ゲームデータとアプリ本体はまだ変更していない。

## 1. 方針

Next.js・TypeScript・ReactFlow・GitHub Pagesの静的配信を維持する。既存の依存グラフ、トレーダー別表示、Kappa/Lightkeeperフィルター、FiR品・ハイドアウト管理を引き継ぎ、データ取得、条件判定、保存、表示の責務を分離する。

最初の完成目標は「選択したゲームモードの最新データで、受注条件と不足条件を説明でき、どの画面でも同じ進捗が表示され、既存の保存データを失わない」こと。全機能の書き直しやサーバー・アカウント管理の導入を前提にしない。

### 採用する追加機能

ユーザーの「全部追加したい」という要望により、以下を初回改修の対象として採用する。表の機能は案の比較ではなく、実装する機能の一覧である。

| 機能 | 表示・操作 | 完了条件 |
| --- | --- | --- |
| 受注できない理由 | 不足PMCレベル、LL、信頼度、前提状態、会話等をノード・一覧・詳細に表示。未知条件は要確認 | 同じタスクならすべての画面で判定と不足理由が一致する |
| ゲーム内状態への手動補正 | 実際の受注可、受注中・完了・失敗を記録。確認時刻と補正解除を用意 | API更新で手動記録を消さず、関連タスクやLLを勝手に変更しない |
| 進捗バックアップ・復元 | プロフィール単位／全体のJSON書き出しと読込。復元前に対象プロフィール・差分をプレビュー | タスク、目標、所持品、施設、信頼度、手動補正、お気に入りを復元できる |
| 更新差分のお知らせ | 前回閲覧したデータとのタスク追加・変更・無効化、必要数量、解放条件、翻訳・補正の変更を表示 | 関連タスクへ移動できる。取得時刻や相場変動だけでタスク更新通知を出さない |
| マップ別の受注中タスクと持ち物 | 出撃するマップを選び、進められる未完了目標と必要キー・マーカー・指定装備等を一覧化 | 複数マップ目標、完了目標、代替品、消耗品と再利用品を正しく扱う |
| 目標までの不足条件一覧 | Kappa／Lightkeeperへの必要タスク、前提、LL、信頼度、会話等をまとめ、各画面へ移動 | 確定した必須条件と未確認条件を区別。LL昇格の選択肢をすべて必須と扱わない |
| 検索・お気に入り | 日英のタスク名・アイテム名で検索。お気に入りを固定表示し、詳細／グラフへ移動 | 名前の変更後もIDでお気に入りを保持。アイテムから関連タスクを検索できる |
| 更新履歴と正常データへの復旧 | データrevision・更新日時・変更概要を表示。互換性のある前の正常版へ戻す操作を用意 | ゲームデータだけを戻し、ユーザー進捗を維持。復旧した版を次回更新で即座に上書きしない |

初回リリースまでにすべて実装するが、共通データ・進捗・判定が整った段階から順に提供する。

## 2. 調査で確認したこと

### 現行ゲームの仕様

公式の1.1.0.0パッチノート（2026-08-03）では、多くのサイドタスクをLLに紐づけ、2〜4件のグループで配布する方式に変更。次のグループは現在のLLのタスクを複数完了するか、次のLLに上がることで解放される。一部の従来型チェーンは残る。LLの取引金額条件は撤廃され、必要PMCレベルと信頼度も変更された。

1.1.5.0（2026-09-08）ではLightkeeperへの入口を再編。「To the Light」の開始にTourでのLighthouse解放、Fence・Refを除くトレーダーLL3、Mechanicとの会話が必要。古い「Getting Acquainted」の前提をすべて収集する方式をそのまま使用できない。

出典: [公式パッチノート](https://steamcommunity.com/app/3932890/announcements/?l=english)。グループの正確な構成や内部カウンターの意味までは、この告知だけでは確定しない。

### APIの実測

公開のJSON APIを実際にGETして確認した。これらはBSGのプレイヤー進捗APIではなく、tarkov.devのコミュニティ製ゲームデータである。

| データ範囲 | モード値 | タスク数 | トレーダー条件あり | 前提タスクあり | その他の条件あり |
| --- | --- | ---: | ---: | ---: | ---: |
| 通常PvP | `regular` | 515 | 110 | 219 | 176 |
| PvE | `pve` | 512 | 110 | 218 | 176 |
| シーズン | `pvp-season` | 489 | 109 | 196 | 176 |

件数は調査時点の配信レコード数で、すべてが現在受注できるタスクであることを意味しない。削除済み・イベント用・未反映のレコードを別途精査する。各タスクフィードのLast-Modifiedは2026-10-06。同日更新であっても内容の完全性は保証されない。

採用候補のエンドポイント:

| エンドポイント | 用途 |
| --- | --- |
| `/endpoints` | 対応モード・言語・配信先の一覧 |
| `/{mode}/tasks` | タスク、前提条件、目標、報酬、Kappa/Lightkeeperフラグ |
| `/{mode}/traders` | トレーダーID、LL別PMCレベル・信頼度条件 |
| `/{mode}/hideout` | 施設、施設レベル・トレーダー・スキル・アイテム条件 |
| `/{mode}/maps` | マップID・表示名の解決。出撃準備で使う情報の詳細構造は実装時に確認 |
| `/{mode}/items` | 参照IDからのアイテム解決。詳細構造と必要データ量は実装着手時に確認 |
| `/{mode}/tasks_en`, `tasks_ja` など | 表示文字列。トレーダー・施設も対応する翻訳ファイルを使用 |
| `/pvp-season/season` | シーズンIDなど。進捗の保存範囲を分けるために使用 |

ベースURL: [json.tarkov.dev](https://json.tarkov.dev/endpoints)。実測したベースデータはIDをキーにしたオブジェクトで、タスクのトレーダーや目標アイテムもID参照。`translations`で指定されたフィールドは翻訳キーになっている。日本語を適用し、欠落時に英語へフォールバックする。実際のタスク名には英語のままの日本語訳もある。

確認した条件:

- `taskRequirements`: タスクIDと許容状態の配列。`active`・`complete`・`failed`を区別する。
- `traderRequirements`: `requirementType`は`level`または`reputation`。`compareMethod`と`value`を含み、整数らしい数値だけでLLと推測してはいけない。
- `otherRequirements`: `dialogue`、`globalVariable`を実測。内部変数IDと閾値は得られるが、その意味や更新契機をこのフィードだけでは確定できない。
- `availableDelaySecondsMin/Max`、`factionName`、`requiredPrestige`も保持する。
- `kappaRequired`・`lightkeeperRequired`が配信されている。表示用フラグと目標自体の解放条件は別に扱う。

具体例として通常PvPのCollectorはPMCレベル42、5件の前提タスク、7トレーダーのLL4、Fence信頼度3以上を配信していた。公式告知の「全トレーダー」という表現からFence・Refまで一律LL4と実装してはいけない。ゲーム内条件との照合後、APIの明示的なトレーダーIDを採用する。

Praporは3モードとも、LL2がPMC6・信頼度0.7、LL3がPMC21・2.7、LL4がPMC36・7.9、取引金額はすべて0だった。数値はコードに固定せずデータから読む。

「Job for a Patriot」「Gunsmith - AS VAL」「The Guide」には内部変数条件を実測した。これを勝手に「特定タスクをN件完了」と解釈しない。調査したフィードのnormalizedName検索では新しい「To the Light」のレコードを特定できず、ストーリー全体のエンドポイントも一覧にない。追加調査・補正の対象とする。

旧GraphQLは前回の実測でサーバーエラーを返した。JSON APIを第一候補にする。GraphQLを自動フォールバックにして異なる形・古い条件のデータを混ぜることは避け、最終正常スナップショットを保持する。

補正候補: [tarkov-data-overlay](https://github.com/tarkovtracker-org/tarkov-data-overlay)。モード別修正、タスク追加・無効化、ストーリー追加、ID単位の条件修正を扱える。[統合仕様](https://github.com/tarkovtracker-org/tarkov-data-overlay/blob/main/docs/INTEGRATION.md)を参考に、必要な補正だけを監査して取り込む。第三者の補正をゲームの公式仕様と同一視しない。採用時は取得リビジョン、差分、根拠を記録し、MITの著作権表示を保持する。

### 既存アプリの確認結果

| 問題 | 根拠・影響 |
| --- | --- |
| 古いデータ | 保存済みタスク491件。FiRデータの生成日時は2026-01-31。トレーダー条件は旧取引金額を含む |
| 解放条件の欠落 | `scripts/fetch-tasks.js`はタスクの`traderRequirements`・`otherRequirements`を取得しない |
| 前提条件の状態を無視 | `TaskTreeView.tsx`は完了ID集合だけで全前提を評価。失敗・受注中で満たせる条件を誤判定 |
| 型の不一致 | `app/types/task.ts`の前提状態は`string`、実データとFiR型は`string[]`。`any`が境界を隠す |
| 画面による判定の違い | グラフは前提タスクを見るが、`FirManager.tsx`の`hasActiveTask`は未完了とPMCレベルだけを見る |
| 保存・同期の分散 | 複数コンポーネントが同じlocalStorageを個別読書き。`ProgressStats`は500msごとにポーリング |
| メモ化の依存漏れ | グラフは`userLevel`・`ignoredTasks`などを依存配列から落とす。FiR側も`ignoredTasks`が不足 |
| 責務の集中 | `TaskTreeView.tsx`は約1120行、`FirManager.tsx`は約630行。保存、集計、条件判定、配置、表示が混在 |
| アイテム要求の表現 | `items[]`を候補ごとに同じ必要数へ展開。複数の代替品をそれぞれ必須と見せる危険がある |
| 目標単位の欠落 | アイテム進捗キーがタスクID＋アイテムID。同一タスクの別目標を区別できない |
| 二重の派生データ生成 | FiR情報を取得スクリプトと`firItemData.ts`で別々に生成。取得日時と集計時刻も混在 |
| 名前での同一視 | FiR索引で同名タスクを除外。別IDやプレステージの意味を失う |
| 一括完了の副作用 | 前提を全部完了扱いにし、PMCレベルも変更。分岐・失敗条件・実際の進捗を再現できない |
| ハイドアウトの条件 | LL条件は取得するが表示モデルから除去済み。以前の画面方針を尊重し、巨大なLL疑似ノードの復活ではなく詳細パネルで扱う |

基準チェック: `npm run lint`は18エラー・17警告。`tsc --noEmit --incremental false`は成功。`npm run build`も通常権限で成功し31ページを静的生成。最初のビルド失敗はサンドボックス内のWindowsパスアクセス制限であり、アプリのビルド不良とは区別する。画面操作による動作検証は未実施。

## 3. 目標となる構造

```text
公開JSON＋翻訳＋監査済み補正
              ↓
取得・検証・正規化 → モード別スナップショット＋manifest
              ↓
ゲーム定義＋プロフィール進捗 → 共通の条件判定・アイテム集計
              ↓
ホーム／タスク一覧／依存グラフ／詳細／FiR／ハイドアウト
```

分割案:

- `src/domain`: タスク・トレーダー・施設・条件・進捗の型、解放判定、依存関係、目標とアイテムの集計。React、localStorage、fetchに依存しない。
- `src/data`: JSON APIのアダプター、翻訳、検証、補正、スナップショットの読込。
- `src/state`: プロフィールと進捗、旧保存形式の移行、購読・バックアップ。
- `src/features`: tasks、traders、items、hideout、profilesのUIとフック。
- `app`: ページ・ルート・レイアウト。既存URLを維持する。
- `scripts`: 一つのデータ更新入口と検証・差分出力。既存更新スクリプトは移行完了後に整理。

フォルダー移動は各機能の置換時に行い、大量移動だけの変更を先行させない。

### 保存と状態

ゲーム定義とユーザー進捗を分ける。プロフィールにはID、モード、シーズンID、陣営、PMCレベル、必要に応じたプレステージ、トレーダー解放・LL・信頼度、タスク状態、目標進捗、施設レベル、必要スキルを保持する。未入力を0と同一視しない。

タスク状態（未着手・受注中・完了・失敗）と、条件から計算する受注可否は別にする。状態変更時刻、手動確認、データ更新で見つからなくなったIDも残す。

LLはPMCレベルと信頼度から計算できるようにするが、未入力・トレーダー未解放・未対応条件を考慮し、ゲーム内のLLを手動記録できる。タスク報酬から信頼度を自動確定しない。初期信頼度やデイリー等もあるため、実測値と将来の獲得見込みを混ぜない。

最初はバージョン付きlocalStorage＋一つの購読可能なストアを使用。React側はSSRに対応した購読方式（例: `useSyncExternalStore`）で読む。同一タブの変更通知と別タブの`storage`イベントを扱う。容量が実際に問題になるならIndexedDBへ移行する。保存先を増やすだけの整理は避ける。

旧形式はバックアップ後、一度だけ変換。旧データにモード情報がないため、移行時に移行先プロフィールを選べるようにし、全モードへ無条件にコピーしない。壊れたJSON、容量不足、存在しないIDでも元データを消さない。旧アイテムカウントの意味は「手動記録した数量」として保持し、曖昧なものを目標への納品済みと断定しない。

### 解放判定

すべての画面が同じ評価関数を使い、`受注可能`・`条件不足`・`要確認`と理由を返す。受注中・完了・失敗などのユーザー状態も併記する。

条件は種類を区別して評価する: PMCレベル、前提タスクの許容状態、トレーダーLL、信頼度と比較演算、陣営、プレステージ、時間経過、会話、ストーリー進行、内部変数、未対応条件。

前提状態の配列は「列挙された状態のいずれか」。条件同士のAND/ORやN件達成は、APIまたは根拠のある補正で明示されたものだけを採用する。グループ解放のORを単純な前提エッジのANDに潰さない。

既知の未達条件があれば条件不足。既知条件は満たすが追加条件を評価できなければ要確認。未知条件を削除して受注可能にしない。ゲーム内で受注できたという手動確認を記録できるようにし、関連タスク・LL・信頼度を勝手に書き換えない。待ち時間の起点が不明なら推定カウントダウンを断定しない。

グループ配布は、最初に変数IDと進行ルールの根拠を集める。対応不能の段階でも最新タスクと既知条件は表示できるようにし、正確なグループ再現ができたと称しない。

### 表示とアイテム

既存グラフを維持し、LL条件・不足信頼度・会話確認等をノード／詳細で説明する。LLごとの一覧を追加し、チェーンは実際の前提関係として表示。正確なグループ情報がないタスクをLL内で勝手に2〜4件の順番へ並べない。

Kappa/Lightkeeperでは「直接必要」「前提として必要」「トレーダー等の条件」を区別。LL昇格のために選択可能な多数のタスクをすべて必須と呼ばない。名前照合による目標の特定をIDベースへ移し、APIフラグの意味と補正内容を検証する。

アイテム要求は目標IDを中心に表現し、候補アイテム集合、数量、FiR、任意条件、耐久等を保持する。代替品は合計N個という一つの要求として集計。所持品、目標への割当、納品済みを分け、同じ所持品を複数の目標へ重複割当しない。従来のタスク別カウントを納品確認として使う場合もUIで意味を明示する。

ハイドアウトはタスクへの無理な型変換をやめ、施設・段階の専用定義を持つ。グラフ部品は再利用し、施設、LL、スキル、アイテムの条件を共通判定へ接続する。

### 出撃準備、検索、目標への導線

マップ別一覧は、プロフィールで受注中と記録したタスクの未完了目標を基本対象にする。条件上受注可能なタスクは別フィルターで追加し、受注中と混同しない。単一の`task.map`だけではなく、各目標の`maps`・ゾーン・指定場所を確認する。マップ不明や任意のマップで達成可能な目標は専用の表示区分へ残す。

出撃予定の目標を選択でき、持ち物チェックリストは選択した目標に合わせて再計算する。マーカー等の消耗品は必要数を集計し、同じキー等の再利用品は重複して要求しない。武器や装備の代替条件は選択肢として表示し、すべて持参する必要があるとは表現しない。APIで持ち物や数量を確定できなければ要確認と表示する。攻略ルートの自動生成や敵位置の推測はこの機能に含めない。

目標の部分達成を記録できるようにし、次回の出撃準備には残りの目標を反映する。持ち物にチェックを付けても、納品・タスク完了・所持品減少を自動的に確定しない。

検索は日本語と英語の表示名、アイテム名・短縮名、関連タスクを対象にする。初期状態で読み込んでいるプロフィールのモードへ範囲を限定し、状態・トレーダー・マップ・Kappa/LKで絞り込める。お気に入りはプロフィール別のタスクIDで保存し、更新で消えたタスクも履歴として残す。検索、固定一覧、マップ一覧、目標チェックリストから同じ詳細・依存グラフへ移動できる。

Kappa/LKの不足一覧は直接必要な条件、前提条件、未確認条件を集約して重複を除く。信頼度の不足量と次に進められるタスクを表示する場合も、実際の受注状態・共通判定・配信された報酬に基づく。ゲーム内会話など未収録の条件は手動確認へ誘導する。

### バックアップ、更新履歴、復旧

進捗のバックアップには保存形式バージョン、書き出し日時、参照していたデータrevisionと全プロフィールを含める。読込時に形式を検証し、復元先と変更内容を表示してから適用する。既存プロフィールの置換と別プロフィールとしての読込を選択でき、置換前のバックアップを残す。未知のIDも捨てず、未対応の新しい保存形式は既存データを変更せず説明する。

更新履歴はゲームデータrevisionごとの意味のある差分を配信する。各プロフィールの最後に確認したrevisionを保存し、未読の変更を一度まとめて表示する。通知を閉じても履歴から再閲覧できる。プロフィールの進捗があるタスクやお気に入りに関する変更を優先表示する。

通常利用者には、アプリと互換性のある直前の正常なゲームデータへ戻す操作を用意する。少なくとも現在版と直前版を取得可能なスナップショットとして配信・保持し、コードのデプロイでも消さない。復旧時は選択したrevisionにプロフィールのデータ参照を固定し、通常の更新確認で自動解除しない。新しい正常版が出たときは切替可能であることを表示し、解除操作を用意する。

サイト管理側には保存した正常スナップショットを再公開する復旧手順と手動実行入口を用意する。問題のあるrevisionを自動更新の採用対象から除外できるようにする。復旧対象の形式が現在のコードと互換でない場合は適用しない。データの復旧とコード自体のロールバック、ユーザー進捗の復元は別操作として扱う。

## 4. 実装の順序と完了条件

| 段階 | 実施内容 | 完了条件 |
| --- | --- | --- |
| 0: 基準と回帰ケース | 既存保存形式の一覧化、データ・UIの問題記録、重要な実例をテストfixture化、Lint問題の分類 | 完了／失敗／受注中、信頼度、未知条件、代替アイテム、旧保存移行を検証できる |
| 1: データ取得基盤 | JSONの3モード、翻訳、ID参照、実行時検証、差分、取得日時・ETag・補正revisionのmanifest。一つの更新コマンド | 3モードが独立。途中失敗で正常データを置換しない。未解決参照・未知条件が報告される |
| 2: 進捗ストアと移行 | 一元保存、プロフィール切替、旧形式のバックアップ・移行、プレビュー付きexport/import、購読 | 旧進捗と新しい記録を復元できる。ホームと詳細とFiRが即時同期。モード・シーズン間で混ざらない |
| 3: 共通解放判定 | 既知条件の評価、状態の区別、未知条件表示、会話／実際の受注可の手動確認 | 境界値と状態のテストが通り、画面間の判定が一致する |
| 4: タスク画面の置換 | TaskTreeViewを配置・表示・操作に分解、LL一覧と不足理由、Kappa/LK不足条件一覧、検索・お気に入り、一括操作の再設計 | ホバーで前提を確認する利点を保持。レベル等の変更が即時反映。検索・固定一覧から詳細へ移動できる |
| 5: FiRと施設 | 目標単位の数量・代替品・所持割当、施設専用モデル、二重集計と同名除外を解消 | 必要数と残数が正しい。同一品・複数目標で二重計上しない。施設条件を説明できる |
| 6: 出撃準備 | マップ別の受注中タスク、未完了目標、選択した目標の持ち物チェックリスト、部分進捗の反映 | 消耗品の数量、再利用キーの重複排除、複数マップ・代替装備が正しい |
| 7: 自動更新と復旧 | 条件付き取得、差分と更新履歴、定期検証・公開、利用者のデータ版固定、管理者の復旧入口 | 変更なしでは不要な公開をしない。異常時は旧版を維持。復旧しても進捗を失わず、即再上書きされない |
| 8: 公開の品質 | 型・Lint・単体／統合チェックと静的ビルドをCIへ。全追加機能、小画面・操作・URL・日本語表示を確認 | 既存URLとGitHub PagesのbasePathが動作。バックアップと復旧を含むチェックがすべて通る |

基本の実装順序は0→1→2→3→4→5→6→7→8。更新差分の生成と復旧用スナップショット保存は段階1から組み込み、段階7で表示・自動公開・復旧操作を接続する。各段階でも必要なチェックを実行し、検証を最後まで先送りしない。段階1〜3の結合テストを終えるまで、旧画面のデータ入口を新形式へ一気に切り替えない。各段階を小さな変更単位にし、旧経路を削除するのは置換の完了後に行う。

段階1で不足データの調査も進め、段階4までにLightkeeper入口と代表的なタスクグループの対応可否を明示する。APIにない条件は根拠付き補正または手動確認で表現する。全ストーリーの専用管理画面は後続拡張とし、必要な解放条件の記録は初回から対応する。

## 5. データ更新と検証

静的配信に合わせ、最初は更新時に取得・正規化した軽量スナップショットを配信する。全アイテムの巨大な生JSONを各ページのJavaScriptへ埋め込まず、必要なアイテム索引を生成し、モード別ファイルは必要時に読み込む。

更新は取得→検証→差分→採用の順。全ファイルが正常なスナップショットを準備してからmanifestを切り替える。HTTP失敗・タイムアウト・翻訳欠落・件数急減・ID参照切れを区別し、重大な欠損は採用を止める。件数だけで正しいデータと判断しない。

ユーザーの追加要望により、自動更新を初回改修の必須機能とする。更新のたびに手動でAPIを叩いたり、JSONを編集する運用をなくす。UIにはデータ取得日時・データrevision・必要な補正・未確認情報を表示する。現在の配信を変えるサーバーAPIはこの段階では不要。

### 自動更新の具体案

GitHub Actionsを6時間おきに実行する初期設定を推奨する。定期実行に加え、手動実行とコードの公開時にも同じ更新処理を使用する。ローカルPCやCodexを起動しておく必要はない。GitHubの定期実行は既定ブランチで動き、混雑時の遅延があるため、正確な更新時刻は保証しない。

```text
定期実行／コード公開／手動再試行
             ↓
API・翻訳・採用済み補正の更新を確認
             ↓
取得・正規化 → 現在配信中のmanifestと意味のある差分を比較
             ↓
変更なし: 終了
変更あり: スキーマ・参照・条件・数量・ビルドを検証
             ↓
正常: 新スナップショットを含むサイトをGitHub Pagesへ配信
異常: 現在の配信を維持し、Actionsの失敗と差分レポートを残す
```

検知はゲームのバージョン番号だけに依存しない。調査したエンドポイント一覧、タスクJSON、GraphQLスキーマには、ゲームのパッチ番号とデータ完全性を結び付ける安定した契約は確認できなかった。ゲーム更新直後にはAPIの反映が遅れることがあり、同じゲームバージョンでもAPI側の補正は発生する。ゲームバージョン情報を今後取得できれば補助情報として保持するが、必須の更新トリガーにはしない。

実測したETag・Last-Modifiedを取得効率化に利用し、対応するAPIでは条件付きGETを使う。ヘッダーが変わっただけでは公開せず、正規化した内容のハッシュで判断する。条件付きGETの304応答動作は実装時に検証する。翻訳や補正だけの変更も対象とする。

トレーダーの次回リセット時刻、取得時刻、変動する相場などはタスク仕様のハッシュから分離する。アイテム価格を配信する場合は価格用revisionと更新頻度を別に持ち、価格変動のたびにタスク仕様変更と誤判定しない。

正常な通常更新は自動公開し、人によるPRのマージを毎回要求しない。定期実行では公開対象のmainのコードを使用し、実行中に作成したデータをビルド成果物へ含める方式を第一案とする。データだけの更新コミットを必須にせず、manifest、意味のある差分、完全な採用スナップショットを復旧用の成果物として保存する。保持期間と復旧先を決め、古いActions成果物が失効して復旧できない状態を避ける。

コード公開時にも同じ取得・採用処理を使い、リポジトリ内の古いJSONへ巻き戻らないようにする。取得不能時に以前のデータでコードを公開する場合は、現在配信中の最終正常スナップショットを検証して使用する。データ更新とコード公開は同じ配信ロックを共有し、古い実行が新しい配信を上書きしないようにする。

未対応スキーマ、解釈不能な新条件、重大な参照欠損、異常な件数急減は公開を止めて差分を残す。既に対応済みの「要確認」条件が含まれること自体は失敗にしない。ゲーム仕様を新たに解釈する必要がある変更まで自動的にコードへ書き換えるとは約束しない。

初回に必要な設定は、Actions・Pagesの有効化と必要なリポジトリ権限の確認。既存の`.github/workflows/deploy.yml`に配信処理があるため、これを共通化して定期データ更新から使用する。公開を伴う実装・有効化は今後の改修時に行い、本計画の更新ではスケジュールを稼働させていない。

アプリ起動時・再読み込み時にも配信manifestを確認し、新しいデータがあれば読込を更新する。ユーザーの進捗は別保存のまま維持し、シーズンIDが変わっても既存プロフィールを自動削除しない。

出典: [GitHub Actionsのschedule仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)、[tarkov.devエンドポイント一覧](https://json.tarkov.dev/endpoints)。ETag・Last-Modifiedは前節の公開API実測による。

重点検証:

- 各種比較演算、LLと信頼度の区別、未入力、負の信頼度、閾値直前／一致／直後。
- 前提の`active`・`complete`・`failed`、複数許容状態、分岐、循環・参照切れ。
- 未知の内部変数、会話条件、時刻の不明な待機、補正の未適用と適用。
- 3モード、シーズン更新、陣営とプレステージ、データ更新後の孤立した進捗ID。
- 一度だけの旧保存移行、破損データ、再読込、同一／別タブ、バックアップ復元。
- 代替アイテム、同一アイテムの複数目標、FiR有無、任意目標、施設との重複割当。
- グラフ／一覧／詳細／FiRの条件一致、PMC・信頼度変更、トレーダー跨ぎの遷移、小画面、キーボード、静的配信のURL。
- マップ別の未完了目標、部分達成、マップ不明、消耗品数量、キーの重複、代替装備と選択目標の持ち物。
- 日英検索、アイテムからの逆引き、更新後の名前変更・削除とお気に入り、プロフィール別の固定一覧。
- 復元プレビュー、全プロフィールのバックアップ、手動補正とお気に入りの復元、未知IDの保持。
- 更新差分の既読管理、互換性のある旧版への復旧、版固定の維持と解除、問題revisionの再採用防止。

現在ないテスト実行基盤はこれらの判定・移行テストのために導入する。単なる表示部品ごとの実装を写したテストは増やさない。Next.js・ReactFlowの大規模なバージョン移行は、本改修に必要な互換性修正がある場合に限り別途評価する。

## 6. 実装開始時の決定事項と残る不確実性

推奨する初期設定は、日本語UI、3モードの選択、端末内保存、既存URL・グラフの維持。ユーザーはPMCレベル・信頼度・LLと実際のタスク状態を入力できる。クラウド同期、ゲームログ自動読取、外部Tracker連携、Battle Pass、装備購入ガイドは初回の改修範囲から外す。

未確定で追加調査するもの:

1. タスク配布グループの内部変数と更新条件、LL到達と完了数のORを復元する方法。
2. 最新Lightkeeper入口・会話・Tour条件のID、旧タスクの有効性、採用する補正。
3. Kappa/LKフラグと前提リストの整合性、モード差、同名・プレステージ・イベントタスクの扱い。
4. アイテムフィードの必要フィールド・価格の鮮度と、各目標の代替品・候補集合の意味。
5. シーズンAPIの期間情報と公式告知の整合性。IDを保存範囲に使うが、期間だけから勝手に進捗をリセットしない。

既存コード内の開発指示に従い、developを起点に`codex/tarkov-modernization`を作成し、既存の修正ブランチをfast-forwardで引き継いだ。データ更新・検証・3モードのスナップショット・条件判定・20件のテストと自動更新ワークフローを実装した。画面と保存形式の移行、追加機能は後続作業。現在はローカル作業で、コミット・push・公開は行っていない。実装詳細は[データ更新手順](DATA_PIPELINE.md)を参照。

API補正が追いつかない期間にも使えることが重要。既知の条件で説明し、未確認部分を隠さず、ゲーム内の実際の状態を記録できる形で完成させる。
